# 代理节点速度实测与调优（2026-10）

本文件记录一次真实环境下的协议横向对比、内核调优效果与 Hysteria2 Brutal 的收益，用来解释脚本里 `nettune()`、systemd 单元写法和 `hyup`/`hydw` 参数的由来。

## 一、测试条件

| 项 | 值 |
|---|---|
| 服务端 | Oracle Cloud 海外 VPS，4 vCPU，Ubuntu 24.04，BBR + fq |
| 客户端 | macOS，中国电信家宽（广州），系统级 TUN 代理 |
| 路径 | RTT **88 ms**，丢包 **0%** |
| 测速对象 | 服务端本地 512MB 静态文件（排除外网抖动），客户端 `curl` 下载 |
| 内核 | 6.8.x，调优后 socket 缓冲区 32MB |

> 为什么不直接测 speed.cloudflare.com：连续请求会被 Cloudflare 返回 403，测出来是 0，容易误判"节点坏了"。要测就用自己服务器上的文件。

## 二、三条结论

1. **网页、视频、单线程场景：QUIC 系（Hysteria2 / TUIC）压倒性优于 TCP 系。** 同一条 88ms 线路，Shadowsocks-2022（TCP）跑 68KB/s，Hysteria2 能跑 3.6MB/s。
2. **运营商对单条 TCP 连接限速，但 UDP 不限。** 同一台机器：TCP 单流 0.88MB/s、8 流 4.63MB/s（靠多连接堆出来），裸 UDP 可以跑到 **252Mbps**。所以"多线程下载快、单线程网页慢"不是节点问题，是链路特性。
3. **Hysteria2 用 Brutal 拥塞控制，比默认 BBR 快 40–80 倍。** 同样一条线路、同一个服务端文件，BBR 只有 0.06–0.11MB/s（几乎不可用），Brutal 单流 4.8–5.5MB/s。

## 三、实测数据

### 3.1 协议对比（调优前 → 调优后）

| 隧道 | 协议 | 调优前 | 调优后 |
|---|---|---|---|
| Shadowsocks-2022 | TCP | 68 KB/s（超时） | 0.06–1.94 MB/s（不稳定） |
| TUIC v5 | UDP/QUIC | 176 KB/s | 2.27–2.85 MB/s |
| Hysteria2（BBR） | UDP/QUIC | 2.49 MB/s | **3.62 MB/s**（两次复测几乎一致＝稳定上限） |

### 3.2 Hysteria2：BBR vs Brutal（服务端本地文件，排除外网干扰）

| 拥塞控制 | 单流 | 4 并发 | 8 并发 |
|---|---|---|---|
| BBR | 0.06–0.11 MB/s | 0.09 MB/s | — |
| **Brutal（声明 300/300 Mbps）** | **4.8–5.5 MB/s** | **9.27 MB/s** | **11.73 MB/s** |

- 把带宽声明从 300 调到 1200Mbps **没有任何额外收益**（单流 5.48、8 并发 11.73），说明瓶颈在路径/QUIC 层，不在参数。
- 服务端 4 核在满速传输时 sing-box 只占 18% CPU、系统 93% idle —— **不是算力瓶颈**。
- 单流天花板 ≈5MB/s，接近 `512KB 初始窗口 ÷ 88ms RTT ≈ 5.8MB/s`，即 quic-go 的流控窗口限制，**只能靠多连接叠加**，调参数无解。

### 3.3 内核调优做了什么

默认 `net.core.rmem_max` 只有 208KB，88ms RTT 下 BDP 需要 3MB 以上才能填满千兆；QUIC 的 socket 缓冲区不够会直接把单流压到 1MB/s 以下。脚本 `nettune()` / `net-tune.sh` 写入 `/etc/sysctl.d/99-agsbx-net.conf`：

```
net.core.rmem_max = 33554432          net.ipv4.tcp_rmem = 4096 87380 33554432
net.core.wmem_max = 33554432          net.ipv4.tcp_wmem = 4096 65536 16777216
net.core.rmem_default = 1048576       net.ipv4.tcp_slow_start_after_idle = 0
net.core.wmem_default = 1048576       net.ipv4.tcp_mtu_probing = 1
net.core.optmem_max = 65536           net.ipv4.tcp_fastopen = 3
net.core.netdev_max_backlog = 16384   net.ipv4.tcp_tw_reuse = 1
net.core.somaxconn = 8192             net.ipv4.tcp_fin_timeout = 15
net.ipv4.ip_local_port_range = 10240 65000
net.ipv4.udp_rmem_min = 16384 / udp_wmem_min = 16384
net.core.default_qdisc = fq / net.ipv4.tcp_congestion_control = bbr   （内核支持时才写）
```

⚠️ 改完必须**重启 sing-box/xray 进程**，QUIC 的 socket 缓冲区在进程启动时确定，不重启不生效。

## 四、Hysteria2 + Brutal 怎么开

服务端（sing-box 入站）需要声明本机带宽，脚本用两个变量控制：

```bash
# hypt=端口 hyup=上行Mbps hydw=下行Mbps
bash <(curl -Ls <脚本地址>) hypt=20443 hyup=300 hydw=300
```

生成的入站会带上 `"up_mbps": 300, "down_mbps": 300, "ignore_client_bandwidth": false`，同时：
- 分享链接追加 `&upmbps=300&downmbps=300`
- sing-box / mihomo 订阅里自动带 `up_mbps`/`down_mbps` 与 `up: "300 Mbps"`/`down: "300 Mbps"`

客户端如果用的是手动导入的旧链接，**必须在客户端里把上行/下行带宽填成一样的值**，否则退回 BBR，收益全没。

### Brutal 的三个坑

1. **带宽必须填真实值**，填 10G 只会让丢包更严重（Brutal 不看丢包，硬压带宽）。
2. **共享带宽 / 按流量计费的机器慎用**，Brutal 会持续顶着声明带宽发包，容易被限速或烧流量。
3. **只有 QUIC 系受益**，TCP 协议（VLESS/SS-2022）与 Brutal 无关，别指望它救 TCP。

## 五、什么场景选什么协议

| 场景 | 推荐 | 理由 |
|---|---|---|
| 网页、4K 视频、SSH、游戏 | Hysteria2（Brutal）或 TUIC | QUIC 不受 TCP 单流限速；Brutal 抗丢包 |
| 大文件多线程下载（aria2/IDM） | TCP 系节点（VLESS-Reality / SS-2022） | TCP 按连接数线性叠加，Hysteria2 的多数连接共享一个拥塞窗口 |
| 需要 CDN / 抗封 IP | Argo 隧道 + VLESS-ws | 走 443 与 CDN 回源 |
| 只有 IPv6 的机器 | Hysteria2 | UDP 不受 v6 路由抖动影响那么明显 |

## 六、systemd 单元为什么这么写

老写法 `After=network.target` + `Restart=on-failure` 有两个真实故障：

- **开机竞态**：`network.target` 只代表网络栈初始化，不代表有 IP。VPS 重启后 sing-box 偶尔先启动、绑定失败退出，`on-failure` 又刚好没接住（干净退出不算 failure），节点直接消失。现改为 `After=network-online.target` + `Wants=network-online.target` + `Restart=always`。
- **崩溃循环刷日志**：配置写错时 `Restart=always` 会每 3 秒重试一次，日志刷爆磁盘（见过 6269 次重启、118 万行日志）。现加 `StartLimitIntervalSec=60` + `StartLimitBurst=5`，5 次失败后停下等人看。
- **高并发下 EMFILE**：默认 `LimitNOFILE=1024`，QUIC 多连接 + 大量 UDP socket 会打满。现设 `1048576`。
- 另加 `SyslogIdentifier`（`journalctl -u sb` 里能区分内核）与常规加固（`ProtectSystem=full`、`NoNewPrivileges`、`PrivateTmp` 等）。

验证方式：`kill -9` 主进程，3 秒内应被拉起且节点可用；`systemctl restart` 后 `journalctl -u sb -n 20` 无反复重启记录。
